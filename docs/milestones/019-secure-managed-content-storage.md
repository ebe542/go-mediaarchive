# Milestone 19: Secure Managed Content Storage

## Goal

Accept authenticated media uploads into server-managed local storage without
trusting client-supplied paths, sizes, or checksums. Persist only opaque relative
storage keys in SQLite and keep absolute filesystem paths out of the public API.

## Scope

- Add a filesystem-backed content store with server-derived paths.
- Persist the relationship between a media identity and its managed content.
- Add an application service that coordinates content storage and metadata
  creation.
- Add an authenticated multipart upload endpoint.
- Calculate content size and SHA-256 while streaming the upload.
- Enforce a configurable upload-size limit.
- Wire the content directory and upload service into the server.
- Add a typed streaming upload operation to the HTTP client.
- Coordinate deletion of managed files and their database records.
- Preserve the existing JSON metadata-creation endpoint for API compatibility.
- Keep content reading, download, range requests, search, and interactive media
  commands outside this milestone.

## Storage model

SQLite continues to store media metadata. A new `media_contents` table associates
one media identity with one opaque relative `storage_key` and a storage timestamp.
The key is generated by the server from the media UUID and does not contain the
original filename.

Managed files reside below a dedicated content root. The content store resolves
all keys relative to that root and rejects absolute paths, parent traversal, and
unexpected key formats. Newly created directories use permission mode `0700` and
files use `0600` on platforms that enforce POSIX permission bits.

The default content root is `data/content`. Server configuration follows the
project precedence rule:

```text
--content-directory flag > MEDIAARCHIVE_CONTENT_DIRECTORY environment variable > data/content default
```

The database stores no absolute path. Moving an archive therefore requires
moving the configured content root without rewriting every content record.

## Upload transaction

An upload is processed in this order:

1. Authenticate the bearer session and authorize media creation.
2. Parse bounded multipart metadata and the file stream.
3. Write the content to a uniquely named temporary file inside the managed
   filesystem.
4. Calculate the byte count and SHA-256 checksum while copying.
5. Reject empty content or content beyond the configured maximum size.
6. Flush and close the temporary file, then atomically rename it to its final
   server-derived location.
7. Persist the media identity and its content location.
8. Remove the managed file if database persistence fails.

The temporary file and final file are on the same filesystem so the final rename
does not expose a partially written file. Compensation handles ordinary
application errors. A process or host failure can still leave an unreferenced
file between the rename and database commit; detecting and reconciling such
orphaned files is explicitly deferred.

## Upload limit

The default maximum upload size is `1 GiB`. It can be overridden with a positive
byte count using:

```text
--maximum-upload-size flag > MEDIAARCHIVE_MAXIMUM_UPLOAD_SIZE environment variable > 1073741824 default
```

The server rejects an oversized request without buffering the complete content
in memory. Multipart form fields and JSON metadata also receive small independent
limits so they cannot consume the file allowance.

## Upload API

The new endpoint is:

| Method | Path | Success | Required global role |
| --- | --- | --- | --- |
| `POST` | `/api/v1/media/uploads` | `201 Created` | editor or administrator |

The request uses `multipart/form-data` with exactly these logical parts:

- `metadata`: JSON containing `title`, `authors`, and `type`;
- `file`: the binary content and its original filename.

The `metadata` part must precede the `file` part, and the file must be the final
part. This ordering permits validation and direct streaming without buffering
the uploaded file.

Size and SHA-256 are intentionally absent from the request metadata because the
server derives both values from the received bytes. The file part media type is
validated and stored as metadata, but it is not treated as proof that the bytes
are safe or conform to a particular file format.

On success, the response uses the existing JSON media representation, including
the server-derived size and checksum, and returns the metadata resource in the
`Location` header. Error responses use the existing JSON error envelope.

The existing JSON `POST /api/v1/media` operation remains available for backward
compatibility and for storage-independent metadata records. Such a record has no
managed content until a future content-replacement operation is introduced.

## Authentication and authorization

The upload endpoint requires a valid bearer session. The application service,
not the HTTP handler or filesystem adapter, applies the existing media-creation
policy. Only active editors and administrators may create media identities.

An uploaded item is owned by the authenticated actor. Neither a client-supplied
owner ID nor a client-supplied storage key is accepted. Administrators receive no
implicit access to content owned by another user.

## Managed deletion

Deletion retains the existing owner or explicit `delete` permission check. For
managed content, the filesystem adapter first atomically moves the file from
its published key to an internal deletion name on the same filesystem. SQLite
then removes the content location, grants, authors, and media identity in one
transaction.

If the database transaction fails, the staged file is restored even when the
request context has already been canceled. After a successful transaction, the
staged file is removed permanently. A final removal failure is reported as an
operational error; the file is no longer addressable through a storage key and
is left for future orphan reconciliation. Metadata-only records continue to use
their existing deletion path.

## Response and logging safety

- API responses never contain content roots, temporary filenames, storage keys,
  database details, or operating-system errors.
- Upload responses use `Cache-Control: no-store`.
- Later content responses will use `X-Content-Type-Options: nosniff`; this
  milestone does not serve uploaded bytes.
- Logs may identify a media UUID and stable error category but must not record
  bearer tokens, uploaded bytes, multipart metadata bodies, or absolute paths.
- Uploaded content, content directories, databases, and real media fixtures
  remain outside version control and release archives.

## Error mapping

| Condition | Status |
| --- | --- |
| Missing, malformed, expired, or revoked session | `401 Unauthorized` |
| Authenticated viewer attempts an upload | `403 Forbidden` |
| Wrong content type, malformed multipart data, missing or duplicate part | `400 Bad Request` |
| Invalid title, authors, type, filename, or media type | `400 Bad Request` |
| Empty file | `400 Bad Request` |
| File or request exceeds its configured limit | `413 Content Too Large` |
| Identifier conflict | `409 Conflict` |
| Content-store, repository, or other operational failure | `500 Internal Server Error` |

Operational failures expose only stable public error messages. Internal
filesystem paths and database errors remain hidden.

## Application and adapter boundaries

The media application layer receives narrow interfaces for managed content and
content-location persistence. It coordinates storage and metadata creation but
does not construct operating-system paths.

The filesystem adapter owns path derivation, temporary files, permissions,
bounded streaming, checksum calculation, atomic rename, and removal. The SQLite
adapter owns the media-to-storage-key association. HTTP code owns multipart
decoding and status mapping without duplicating media authorization.

## Typed client

The typed client accepts metadata plus an `io.Reader` and streams multipart
content directly to the server. It does not read the complete source into memory
and does not retry a partially transmitted upload automatically. The caller
retains responsibility for reopening a source before an explicit retry.

The client returns the existing typed media response and preserves cancellation,
timeouts, TLS trust, bearer authentication, response-size limits, JSON content
validation, and structured API errors.

## Implementation sequence

1. Define the storage, upload, API, and security contracts in this document.
2. Add the filesystem content store and focused adapter tests.
3. Add SQLite content-location persistence and migration tests.
4. Add the upload application service, compensation behavior, and service tests.
5. Add coordinated deletion for managed media.
6. Add the authenticated multipart endpoint and server composition.
7. Add typed streaming upload support and complete the milestone documentation.

Each implementation step is delivered as a complete Conventional Commit. Tests
remain in the same commit as the behavior they specify.

## Out of scope

- Content streaming and inline reading
- Explicit persistent download
- HTTP range and conditional requests
- Content replacement
- Media search, filtering, and pagination
- Interactive client and administrator media commands
- Deep format validation or malware scanning
- Orphaned-file reconciliation after process or host failure
- Filesystem encryption at rest
- Object storage and remote storage providers
- Audit-log persistence
- mTLS client authentication
- PostgreSQL persistence
